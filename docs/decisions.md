# Решения проекта

Записываем принятые решения кратко: **Вопрос → Решение → Альтернативы (если рассматривались) → Причина → Последствия (при необходимости)**. Вопрос отражает исходную потребность, а не свойства выбранного решения.

Заголовок: `D-001. Название`; область можно указать перед названием, например `API: обязательность полей`.

Журнал опубликованных решений ведём по принципу WAL: новые записи добавляем только в конец, закоммиченные не переписываем. При пересмотре или исправлении добавляем новую запись со ссылкой на прежнюю и явно указываем, что заменяем или уточняем. Незакоммиченные черновики уточняем перед согласованием и коммитом.

## D-001. Схемы запросов и ответов API

**Вопрос:** как убрать дублирование полей запросов и ответов?

**Решение:** `ThreatData` содержит изменяемые сведения и используется в PUT. `Threat` дополняет её обязательным `md5` через `allOf` и используется в POST и успешных ответах. В ответах обязательны `md5` и `name`.

**Причина:** при создании клиент передаёт оба поля, при замене — `name`, а MD5 задан в пути. Сервис сохраняет эти данные и всегда может вернуть их. Общая схема упрощает расширение модели.

**Последствия:** контракт успешного ответа становится строже: исходная схема допускала отсутствие `md5` и `name`, новая требует оба поля. Для существующих HTTP-клиентов это совместимое усиление гарантий сервера; требования к запросам не изменяются. Версия контракта повышена до `1.1.0`.

## D-002. Регистр MD5

**Вопрос:** что делать с тем, что пользователь может прислать MD5 в любом регистре?

**Решение:** принимать MD5 в любом допустимом контрактом регистре; хранить и возвращать в нижнем.

**Причина:** разные написания одного хеша должны обозначать одну запись и попадать под одно ограничение уникальности.

## D-003. Инструменты тестирования

**Вопрос:** использовать ли фреймворк для тестов или обойтись встроенными средствами Go?

**Решение:** использовать `testify` вместе со стандартным пакетом `testing`.

**Причина:** удобные и читаемые проверки сокращают повторяющийся код тестов; средства мокирования доступны в той же библиотеке для последующих задач.

## D-004. Организация проверок CI

**Вопрос:** стоит ли распараллеливать проверки CI для нашего микросервиса или выполнять их последовательно?

**Решение:** выполнять проверки последовательно в одном job на одной машине.

**Причина:** на текущем этапе сами проверки ожидаются быстрыми, поэтому сочли эффективнее запускать их подряд без затрат на подготовку отдельных машин для каждого job.

**Последствия:** может увеличиться время обратной связи при ошибках CI.

## D-005. Конфигурация приложения

**Вопрос:** как задавать базовые настройки приложения и переопределять их для другого окружения?

**Решение:**

- Явно указанный YAML → переопределения env → проверка результата. Без YAML — только env.
- Базовые значения — в `config/config.yaml`, без дублирования defaults в Go.
- Имена env соответствуют полным путям настроек в YAML.

**Причина:** env позволяют менять настройки окружения без правки файла и пересборки приложения. Базовые значения имеют один источник.

## D-006. Локальные реквизиты подключения

**Вопрос:** как хранить реквизиты локальной БД, не включая пароль в Git и образ приложения?

**Решение:**

- Локальные реквизиты — в `.env` с доступом только владельцу; файл исключён из Git и Docker build context.
- В репозитории — `.env.example` без настоящего пароля; в базовом YAML реквизиты не дублируются.
- Приложение получает реквизиты через окружение, само `.env` не читает. Значения настроек в ошибки не включаются.

**Причина:** для локального задания достаточно файла с ограниченным доступом. Шаблон позволяет настроить подключение, не сохраняя пароль в репозитории.

## D-007. Библиотеки загрузки конфигурации

**Вопрос:** какие библиотеки использовать для чтения YAML и переменных окружения?

**Решение:** `goccy/go-yaml` для YAML, `caarlos0/env/v11` для env.

**Альтернативы:** `cleanenv` — единая библиотека загрузки YAML и env.

**Причина:** выбранные версии библиотек покрывают нужные источники и не имеют внешних модульных зависимостей. `cleanenv` дополнительно зависит от парсеров неиспользуемых форматов.

## D-008. Выбор СУБД

**Вопрос:** какую СУБД использовать для хранения сведений об угрозах?

**Решение:** PostgreSQL.

**Альтернативы:** SQLite и MySQL.

**Причина:** для задания достаточно SQLite, но PostgreSQL выбран для демонстрации работы с серверной БД. MySQL подходит технически, однако у автора нет опыта работы с ним.

## D-009. Применение изменений схемы

**Вопрос:** как применять изменения схемы при развёртывании сервиса?

**Решение:** штатный Goose CLI в одноразовом контейнере Compose после готовности PostgreSQL. SQL-миграции транзакционные; изменения добавляются новыми файлами, применённые файлы не редактируются. Down автоматически не запускается.

**Альтернативы:** собственная Go-команда миграций.

**Причина:** для SQL-миграций без прикладной логики достаточно готового CLI. Отдельный этап позволяет применять и проверять изменения схемы независимо от приложения.

**Последствия:** запускать один мигратор за раз: защиты от параллельных запусков нет. Ошибка откатывает текущую миграцию, сохраняя ранее завершённые.
